# Operation processing contract

## State model
- `pending`: accepted durably; waiting for dispatch.
- `processing`: a worker owns an execution attempt.
- `retry_scheduled`: transient failure; PostgreSQL stores `nextAttemptAt`.
- `acknowledged`: handler confirms the business outcome.
- `dead_letter`: terminal failure; a durable `OperationDeadLetter` row exists.

## Required handler guarantees
Every handler validates its payload/schema version, derives actor and organization from the persisted operation, re-checks resource ownership in the same tenant, uses transactional idempotency, ignores client-supplied identity/approval/status fields, and treats external provider timeouts as ambiguous until reconciled.

## Phase 1C registered operation

The first registered handler is deliberately narrow:
- operation type: `crud`
- action: `EXPENSE_CREATE`
- schema version: `1`
- required payload: business ID, amount, category, description, ISO date, VAT amount and VAT eligibility.

The handler requires the business owner and `Business.organizationId` to match the persisted operation. It writes the expense plus an `operation_effects` receipt in one serializable PostgreSQL transaction. The receipt is unique on `operation_id`; concurrent duplicate execution rolls back the losing transaction and is retried against the committed receipt. The payload cannot choose user, organization, status, approval, or payment state.

Business records are organization-bound on creation. Legacy businesses are backfilled only when the owner has exactly one active organization membership; ambiguous/unmapped rows remain unbound and cannot receive offline writes until explicitly reconciled.

Other CRUD actions and all `sync`, `filing`, and `payment` operations remain unsupported and fail closed. VAT eligibility is required explicitly; this handler does not infer tax treatment.

### Phase 1C.2 invoice draft operation

The CRUD allow-list also accepts `INVOICE_CREATE` at schema version 1. The backend validates line-item arithmetic and requires VAT to be explicitly supplied; it does not infer a tax rate or calculate tax eligibility. It re-checks active membership and business ownership/organization binding, then creates a `draft` invoice and the operation-effect receipt in one serializable transaction.

The handler does not assign an invoice number, stamp or submit to NRS, send an invoice, initiate payment, or mark the invoice as tax compliant. These are separate workflows and remain outside this operation. The mobile offline queue accepts `INVOICE_CREATE` after SQLite schema migration v8. Existing pending rows are preserved by the table rebuild.

### Phase 1C.3 receipt evidence infrastructure

Receipt upload intents are created through authenticated `POST /api/v1/receipts/upload-intents`. The server verifies the active organization context, requires the business owner and organization binding to match, generates an opaque object key, and persists a pending evidence record before issuing a short-lived R2-compatible presigned PUT URL. Only JPEG, PNG, WebP and PDF are accepted; maximum object size is 10 MiB.

The client must upload using the exact signed content type and SHA-256 metadata headers, then call `POST /api/v1/receipts/:id/complete`. Completion downloads at most the declared 10 MiB staging object, verifies actual byte count, content type, SHA-256 digest and file signature, then conditionally copies the pinned ETag to a separate server-only evidence key before marking evidence `UPLOADED`. The presigned URL can only write to the staging key, so it cannot mutate the promoted evidence object after verification. Client-supplied storage keys are never accepted. Evidence metadata is tenant-bound and retention-dated; both object keys are opaque and generated by the server.

The offline CRUD allow-list accepts `RECEIPT_ATTACH` only for a server-issued evidence ID already verified by the completion endpoint. The handler rechecks active membership, receipt ownership, business and expense linkage, then attaches evidence and writes the idempotency receipt in one serializable transaction. Multiple receipts may be attached to one expense; a receipt can be attached only once.

This milestone does not implement OCR, malware scanning, content disarm/reconstruction, receipt deletion, or a complete mobile camera/gallery upload experience. Those remain explicit follow-on controls; do not treat the initial file signature check as malware scanning.

## Payment and filing rule
Payment initiation and filing operations must never be automatically replayed after an ambiguous external outcome. Recovery requires explicit authorization and provider reconciliation.

## Release gate
The pipeline is not production-ready until remaining handlers, audited resolution controls, contract compatibility tests, and PostgreSQL-backed end-to-end integration tests pass.

### Phase 1C.4 receipt quarantine, malware scanning and OCR

The completion endpoint now promotes byte-verified uploads into a private quarantine key and creates a durable PostgreSQL processing job in the same transaction as the `QUARANTINED` state transition. The processing worker claims jobs with `FOR UPDATE SKIP LOCKED`, retries transient infrastructure failures with bounded exponential backoff, and dead-letters after five attempts. An absent or unreachable ClamAV daemon is never interpreted as a clean verdict.

The worker scans the exact SHA-256-bound bytes using ClamAV INSTREAM. A clean result is recorded once in `receipt_scan_results`; only then is the object conditionally copied to a separate opaque clean key and evidence marked `CLEAN`. Infected evidence is marked `INFECTED`, audited and deleted from quarantine on a best-effort basis. Attachment now requires `CLEAN`, preventing pending, failed or infected documents from entering expense records.

After a clean scan, Google Cloud Vision document OCR may persist a bounded text extraction and mean block confidence in `receipt_ocr_extractions`. OCR is evidence extraction only: no tax classification, VAT eligibility, tax computation, invoice mutation or NRS submission is performed. OCR provider failure is recorded as `UNAVAILABLE` for human review and does not change the malware verdict. Scan and OCR records are append-only by unique receipt key; raw provider output is not retained.

Required worker configuration: `CLAMAV_HOST` and optional `CLAMAV_PORT` (default 3310), plus Google Application Default Credentials for OCR. Until the scanner is reachable, evidence remains quarantined and cannot be attached. The clean object key is server-only; no public download route is introduced.

Operational prerequisites before production: deploy the migration, provision a private R2 bucket policy separating quarantine and clean prefixes, allow the worker to access both prefixes, test ClamAV EICAR detection and clean fixtures, validate Google Vision credential isolation/data residency, and exercise worker lease recovery and retry/dead-letter behavior. OCR data contains potentially sensitive receipt content and must be protected by the same tenant access controls and retention policy as the source evidence.
