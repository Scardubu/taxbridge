# Operation processing contract

## State model
- `pending`: accepted durably; waiting for dispatch.
- `processing`: a worker owns an execution attempt.
- `retry_scheduled`: transient failure; PostgreSQL stores `nextAttemptAt`.
- `acknowledged`: handler confirms the business outcome.
- `dead_letter`: terminal failure; a durable `OperationDeadLetter` row exists.

## Required handler guarantees
Every handler validates its payload/schema version, derives actor and organization from the persisted operation, re-checks resource ownership in the same tenant, uses transactional idempotency, ignores client-supplied identity/approval/status fields, and treats external provider timeouts as ambiguous until reconciled.

## Phase 1C registered operation

The first registered handler is deliberately narrow:
- operation type: `crud`
- action: `EXPENSE_CREATE`
- schema version: `1`
- required payload: business ID, amount, category, description, ISO date, VAT amount and VAT eligibility.

The handler requires the business owner and `Business.organizationId` to match the persisted operation. It writes the expense plus an `operation_effects` receipt in one serializable PostgreSQL transaction. The receipt is unique on `operation_id`; concurrent duplicate execution rolls back the losing transaction and is retried against the committed receipt. The payload cannot choose user, organization, status, approval, or payment state.

Business records are organization-bound on creation. Legacy businesses are backfilled only when the owner has exactly one active organization membership; ambiguous/unmapped rows remain unbound and cannot receive offline writes until explicitly reconciled.

Other CRUD actions and all `sync`, `filing`, and `payment` operations remain unsupported and fail closed. VAT eligibility is required explicitly; this handler does not infer tax treatment.

### Phase 1C.2 invoice draft operation

The CRUD allow-list also accepts `INVOICE_CREATE` at schema version 1. The backend validates line-item arithmetic and requires VAT to be explicitly supplied; it does not infer a tax rate or calculate tax eligibility. It re-checks active membership and business ownership/organization binding, then creates a `draft` invoice and the operation-effect receipt in one serializable transaction.

The handler does not assign an invoice number, stamp or submit to NRS, send an invoice, initiate payment, or mark the invoice as tax compliant. These are separate workflows and remain outside this operation. The mobile offline queue accepts `INVOICE_CREATE` after SQLite schema migration v8. Existing pending rows are preserved by the table rebuild.

### Phase 1C.3 receipt evidence infrastructure

Receipt upload intents are created through authenticated `POST /api/v1/receipts/upload-intents`. The server verifies the active organization context, requires the business owner and organization binding to match, generates an opaque object key, and persists a pending evidence record before issuing a short-lived R2-compatible presigned PUT URL. Only JPEG, PNG, WebP and PDF are accepted; maximum object size is 10 MiB.

The client must upload using the exact signed content type and SHA-256 metadata headers, then call `POST /api/v1/receipts/:id/complete`. Completion downloads at most the declared 10 MiB staging object, verifies actual byte count, content type, SHA-256 digest and file signature, then conditionally copies the pinned ETag to a separate server-only evidence key before marking evidence `QUARANTINED` and atomically enqueuing malware processing. The presigned URL can only write to the staging key, so it cannot mutate the promoted quarantine object after verification. Client-supplied storage keys are never accepted. Evidence metadata is tenant-bound and retention-dated; both object keys are opaque and generated by the server.

The offline CRUD allow-list accepts `RECEIPT_ATTACH` only for a server-issued evidence ID that has reached `CLEAN` after malware scanning. The handler rechecks active membership, receipt ownership, business and expense linkage, then attaches evidence and writes the idempotency receipt in one serializable transaction. Multiple receipts may be attached to one expense; a receipt can be attached only once.

This milestone does not implement OCR, malware scanning, content disarm/reconstruction, receipt deletion, or a complete mobile camera/gallery upload experience. Those remain explicit follow-on controls; do not treat the initial file signature check as malware scanning.

## Payment and filing rule
Payment initiation and filing operations must never be automatically replayed after an ambiguous external outcome. Recovery requires explicit authorization and provider reconciliation.

## Release gate
The pipeline is not production-ready until remaining handlers, audited resolution controls, contract compatibility tests, and PostgreSQL-backed end-to-end integration tests pass.

### Phase 1C.4 receipt quarantine, malware scanning and OCR

The completion endpoint now promotes byte-verified uploads into a private quarantine key and creates a durable PostgreSQL processing job in the same transaction as the `QUARANTINED` state transition. The processing worker claims jobs with `FOR UPDATE SKIP LOCKED`, retries transient infrastructure failures with bounded exponential backoff, and dead-letters after five attempts. An absent or unreachable ClamAV daemon is never interpreted as a clean verdict.

The worker scans the exact SHA-256-bound bytes using ClamAV INSTREAM. A clean result is recorded once in `receipt_scan_results`; only then is the object conditionally copied to a separate opaque clean key and evidence marked `CLEAN`. Infected evidence is marked `INFECTED`, audited and deleted from quarantine on a best-effort basis. Attachment now requires `CLEAN`, preventing pending, failed or infected documents from entering expense records.

After a clean scan, Google Cloud Vision document OCR may persist a bounded text extraction and mean block confidence in `receipt_ocr_extractions`. OCR is evidence extraction only: no tax classification, VAT eligibility, tax computation, invoice mutation or NRS submission is performed. OCR provider failure is recorded as `UNAVAILABLE` for human review and does not change the malware verdict. Scan and OCR records are append-only by unique receipt key; raw provider output is not retained.

Required worker configuration: `CLAMAV_HOST` and optional `CLAMAV_PORT` (default 3310), plus Google Application Default Credentials for OCR. Until the scanner is reachable, evidence remains quarantined and cannot be attached. The clean object key is server-only; no public download route is introduced.

Operational prerequisites before production: deploy the migration, provision a private R2 bucket policy separating quarantine and clean prefixes, allow the worker to access both prefixes, test ClamAV EICAR detection and clean fixtures, validate Google Vision credential isolation/data residency, and exercise worker lease recovery and retry/dead-letter behavior. OCR data contains potentially sensitive receipt content and must be protected by the same tenant access controls and retention policy as the source evidence.

Every newly scanned receipt enters `reviewStatus=REQUIRED`. The tenant owner must explicitly call `POST /api/v1/receipts/:id/review` with `ACCEPT` or `REJECT`; the review transition and audit event commit atomically. Offline attachment requires both malware state `CLEAN` and `reviewStatus=ACCEPTED`. OCR confidence and text remain evidence candidates and never auto-approve or determine tax treatment. PDF OCR is currently marked unavailable pending a dedicated asynchronous PDF document processor; it remains eligible for manual review after a clean malware verdict.

The authenticated `GET /api/v1/receipts/:id/download` endpoint issues a 60-second private presigned URL only after a matching CLEAN scan record exists. It never signs the quarantine or staging key. This gives the tenant owner access to the original clean evidence for human review without exposing storage credentials or persistent public URLs.

### Phase 1C.5 mobile receipt capture and restart recovery

The mobile receipt flow now copies camera/gallery input into app-private persistent document storage and writes a SQLite `receipt_upload_sessions` row (schema v10) before making a network request. The local session stores a client-generated UUID, business/file metadata, byte size, SHA-256, server evidence ID, processing/review status and retry metadata. The source file is retained while upload or verification is ambiguous; it is removed only after the server reports a verified non-pending state.

The client-generated `clientUploadId` is persisted under a unique nullable database constraint. Upload-intent creation uses an idempotent Prisma upsert bound to the authenticated user and organization and rejects reuse with different metadata. Repeated requests issue a fresh five-minute presigned URL for the same pending evidence ID. Older clients that omit `clientUploadId` remain compatible but do not receive client-side crash-recovery guarantees.

A failed or interrupted single-object PUT is retried from byte zero with a renewed URL and the same expected digest. This is restartable retry, not multipart/chunk-level resume; the 10 MiB limit keeps the upload atomic and bounded. The application retries only when NetInfo reports connectivity, and replays incomplete sessions after startup or connectivity restoration. A completion timeout first checks the tenant-scoped status endpoint before deciding whether another PUT is needed.

The receipt screen now supports camera and image-library capture, displays quarantine/scanning state, supports explicit status refresh, opens a short-lived clean-only preview, and requires the user to accept or reject the scanned evidence. Receipt attachment continues to require the backend's CLEAN scan and ACCEPTED review state. Local accounting receipt records and their existing offline sync remain separate from server evidence verification; a local receipt save is not proof of a malware-cleared evidence record.

SQLite v10 creates the durable recovery table without rebuilding or rewriting the existing offline-operation queue. Migration tests must exercise v9 to v10 and confirm existing receipts, offline operation IDs, retry counters and next-attempt timestamps remain unchanged.


### Phase 1C.6 invoice lifecycle governance

Business-bound invoices now have an internal approval state independent from the operational invoice status and NRS fields:

- `DRAFT`: editable only through the tenant-scoped, expected-version draft endpoint.
- `PENDING_APPROVAL`: content is frozen while an authorized reviewer decides.
- `APPROVED`: records the reviewer and the exact approved invoice revision.
- `REJECTED`: records a mandatory reason; the draft must be substantively changed, creating a new immutable revision, before resubmission.

The API is mounted under `/api/v1`:
- `PATCH /invoices/:id/draft` — full replacement of the validated financial/document fields with `expectedVersion`.
- `POST /invoices/:id/submit-for-approval` — freezes the current revision for review.
- `POST /invoices/:id/approve` and `POST /invoices/:id/reject` — owner/admin-only maker-checker transitions. The creator cannot review their own invoice.
- `GET /invoices/:id/lifecycle` — tenant-scoped revision and event history.

Each content revision is stored in `invoice_versions` with a SHA-256 content hash. Lifecycle events are stored separately in `invoice_lifecycle_events`; PostgreSQL triggers reject updates and deletes to both history tables. Draft mutation, revision creation, and lifecycle event append commit in one serializable transaction. Transition updates use compare-and-swap on the invoice version and approval state. A stale revision returns a conflict rather than silently overwriting concurrent work.

The Phase 1C operation handler and authenticated invoice-management create route create business-bound invoices as internal drafts with an initial revision/event. The legacy invoice update/cancel paths reject business-bound invoices. The device-sync API rejects malformed IDs, cross-user invoice references and business-bound invoice mutations before enqueue; the worker repeats ownership and lifecycle checks when executing queued work. Bulk invoice status updates are disabled, legacy bulk cancellation is limited to eligible unbound invoices, and invoice export is scoped to the active organization. The direct Duplo resubmission endpoint, admin NRS retry path and NRS submission service require approval of the exact current revision before external submission, including forced retries.

Approval is not NRS compliance, stamping, submission, delivery, payment authorization, or tax filing. This phase does not initiate an external provider call or set `nrsCompliant=true`. Existing legacy invoices receive a revision snapshot where one is missing and a `LEGACY_IMPORTED` event only when their business is already organization-bound; prior approval is never inferred from a legacy operational status or NRS reference.

The approval endpoint requires owner/admin membership and rejects self-approval. Draft editing is allowed to the creator or an owner/admin; accountants may submit drafts for approval. Business-bound invoices without an active organization binding remain outside this lifecycle and fail closed. Cancellation, delegated approval matrices, NRS submission authorization scopes, PDF/UBL artifact versioning, and approval notifications are not part of this milestone.
The NRS status detail, summary and health endpoints are mounted in the active Fastify application, require authentication, and scope invoice queries/aggregates to the requesting user. Business-bound invoices can be marked sent only after NRS stamping; approval alone does not authorize a send transition.

Validation required before production: Prisma validate/generate and migration deployment against a clean PostgreSQL database; lifecycle integration tests covering maker-checker, rejected-revision resubmission, stale versions, tenant isolation and immutable-history triggers; regression tests for all legacy mutation/submit paths; and full backend/mobile CI. The migration and tests have been authored but not executed in the current environment.
